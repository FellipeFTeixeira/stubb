- [2026-10-24] "Fase" se refere ao roadmap do projeto (`docs/roadmap.md`); "Etapa" se refere aos passos do pipeline SDD. **Como aplicar:** usar os termos de forma consistente em docs e conversas.
- [2026-10-24] O `gh` está logado como `fellipeftg`, que tem permissão de admin no repo `FellipeFTeixeira/stubb`. O worktree `duvidas` que existia em `orca/workspaces` já não existe mais (verificado em 2026-10-27). **Como aplicar:** não estranhar a diferença de login.
- [2026-10-24] Subagentes do Claude Code aceitam `model` e `effort` no frontmatter de `.claude/agents/*.md`, e por padrão rodam em background. **Como aplicar:** esperar a notificação de conclusão do subagente; não presumir o resultado.
- [2026-10-24] O usuário não quer usar o Docker Desktop. O runtime é o Docker Engine no Ubuntu 26.04 do WSL2 (systemd ativo), exposto em `tcp://127.0.0.1:2375`, e o CLI do Windows usa o contexto `wsl-engine`. Dentro do Ubuntu, `docker` no PATH pode resolver para o binário do Docker Desktop em `/mnt/c/...`; use `/usr/bin/docker`. **Como aplicar:** nunca sugerir iniciar o Docker Desktop; para checar o daemon, rodar `docker --context wsl-engine info`.
- [2026-10-24] O WSL desliga a distro Ubuntu quando não há processo Windows ligado a ela, e o `dockerd` cai junto (conexões TCP do CLI não mantêm a distro viva). Um `wsl.exe -d Ubuntu --exec sleep infinity` em segundo plano mantém a distro ligada. **Como aplicar:** se `docker info` der "connection refused" em 127.0.0.1:2375, conferir `wsl -l -v` e subir o keepalive com `Start-Process -WindowStyle Hidden wsl.exe -ArgumentList '-d','Ubuntu','--exec','sleep','infinity'`.
- [2026-10-24] Com o WSL em NAT (padrão), o CLI do Windows via `tcp://127.0.0.1:2375` recebia stdout vazio em `docker run`/`docker exec` (exit code ok). O repasse de portas do WSL não transmite o fluxo de attach. Corrigido com `networkingMode=mirrored` em `%USERPROFILE%\.wslconfig` + `wsl --shutdown`. **Como aplicar:** se o stdout do docker sumir, conferir se o `.wslconfig` ainda tem `mirrored`; no modo mirrored, porta publicada por container conflita com serviço do Windows na mesma porta.
- [2026-10-24] Com o engine no WSL e o compose rodando no Windows, bind mounts relativos falham ("invalid volume specification C:\..."). A correção tem duas partes: o symlink `/c -> /mnt/c` na distro Ubuntu, que o `infra/scripts/docker-up.ps1` recria, e a variável de usuário do Windows `COMPOSE_CONVERT_WINDOWS_PATHS=1`, já definida com `setx`. Isso não afeta o build de imagens. **Como aplicar:** terminais abertos antes do `setx` não enxergam a variável; num shell antigo, definir `$env:COMPOSE_CONVERT_WINDOWS_PATHS=1`. Em `docker run -v`, usar caminho `/c/...` ou `/mnt/c/...`, não `$(pwd -W)`.
- [2026-10-24] O Windows reserva faixas de porta TCP dinâmicas (Hyper-V/WSL), e com o WSL em mirrored o docker não publica portas dentro delas. Em 2026-10-24 a faixa excluída era 50000-50059 e 56946-57545. Essas faixas podem mudar depois de um reboot. **Como aplicar:** antes de escolher porta publicada, rodar `netsh interface ipv4 show excludedportrange protocol=tcp`; se um container não subir por porta, conferir essa lista primeiro.
- [2026-10-24] O Bash tool (Git Bash) falha com "unexpected EOF" num comando com muitos heredocs ou heredoc aninhado, e nada roda, nem as partes iniciais. Heredoc Python também lê acento com a codificação errada. **Como aplicar:** criar arquivos com a ferramenta Write e editar com Edit; no Board, que outro agente pode estar editando, reler antes e usar trechos pequenos.
- [2026-10-24] O lint tipado (typescript-eslint) reprova padrões comuns de teste: `res.body` e `app.getHttpServer()` do supertest (`no-unsafe-*`), `expect(obj.method)` em mock (`unbound-method`) e `const { x: _x, ...rest }` (`no-unused-vars`). O React Compiler lint (`react-hooks/purity`) reprova `performance.now()` em callback. **Como aplicar:** helpers tipados (`body<T>(res)`, cast para `Server` de `node:http`), guardar o `vi.fn()` numa variável, `Object.fromEntries` com filtro e um wrapper `nowMs()`.
- [2026-10-24] O Vitest do projeto roda sem globals: o Testing Library não limpa sozinho (o `setup.ts` do web faz `afterEach(cleanup)`), e o Vitest injeta `BASE_URL='/'` no ambiente. **Como aplicar:** não usar `BASE_URL` como variável de configuração (o e2e usa `E2E_BASE_URL`).
- [2026-10-24] No host Windows com o WSL em mirrored, `localhost` resolve primeiro para `::1` e as portas publicadas pelo engine não respondem nele (timeout, às vezes intermitente); `127.0.0.1` funciona em todas. Efeitos: o librdkafka tenta IPv6 primeiro e leva cerca de 11 s até cair no IPv4, e o navegador parece não achar a stack. O `netstat` do Windows não lista essas portas (quem as detém é o WSL). **Como aplicar:** clientes Kafka que rodam no host usam `'broker.address.family': 'v4'`; ao orientar o usuário ou testar acesso, usar `http://127.0.0.1:<porta>`; antes de procurar processo na porta, testar `127.0.0.1` vs `::1`.
- [2026-10-24] `nest start --watch` em imagem `-slim` precisa de `procps` (o tree-kill usa `ps`); sem ele, cada recompilação dá `EADDRINUSE`. O `TypeORM migration:generate` roda sobre o `dist/`, então rodar `nest build` antes. **Como aplicar:** manter `procps` no target `dev` do Dockerfile.
- [2026-10-24] O teste de replay para o projector e sobe de novo com `docker compose up`. Se o compose falhar no meio (por exemplo, sem `COMPOSE_CONVERT_WINDOWS_PATHS`), o projector fica parado e os testes de query seguintes dão 404 em cascata. **Como aplicar:** se o E2E falhar em `queries`, conferir `docker compose ps` e a variável antes de investigar código; em sessão aberta antes do `setx`, definir `$env:COMPOSE_CONVERT_WINDOWS_PATHS='1'`.
- [2026-10-24] `pnpm install` do pnpm 12 grava `minimumReleaseAgeExclude` no `pnpm-workspace.yaml` (política de idade mínima de release) e exige `allowBuilds` para dependência com binário nativo (confluent). O `shadcn` 4.x exige `src/index.css` com `@import "tailwindcss"` antes do `init` e gera `cn` a partir do pacote `cn` (do próprio shadcn). **Como aplicar:** não remover essas entradas; ao adicionar dependência nativa, incluir em `allowBuilds`.
- [2026-10-24] Na implementação em paralelo, nenhum agente rodou o lint completo antes de fechar a trilha (a trilha I só rodou o Prettier), e o thread principal pegou a falha. **Como aplicar:** a verificação do thread principal roda sempre o `pnpm lint` da raiz ao fim de cada onda, antes de disparar a próxima.
- [2026-10-24] `sudo` no Ubuntu do WSL pede senha, mas `wsl -d Ubuntu -u root -- <cmd>` roda como root sem senha. O pnpm foi instalado sem admin com `corepack enable pnpm --install-directory "$env:APPDATA\npm"` (pasta já no PATH do usuário). O Node 24.22.1 veio do winget (`OpenJS.NodeJS.LTS`), com UAC. **Como aplicar:** para instalar algo no WSL, usar `-u root`; para shims do corepack, usar `--install-directory` em vez de admin.
- [2026-10-24] O usuário quer subagentes em paralelo sempre que possível (principalmente na implementação), com memória interligada, para não sobrecarregar um agente só. Decidido: até 4 implementers por onda, mesmo working tree com arquivos donos exclusivos por trilha, Board por feature em `SDD/WORK/` + `SendMessage` entre agentes; pesquisa grande também é dividida. **Como aplicar:** ao disparar implementers, criar o Board, mandar a onda inteira numa mensagem só e registrar os IDs dos agentes no Board logo depois do spawn (agentes irmãos não se conhecem no momento do spawn).
- [2026-10-27] O OOM vinha do WSL sem teto (`.wslconfig` só com `mirrored`, 50% da RAM de 13,9 GB). Medido: stack em prod usa cerca de 1,4 GB nos containers; em dev (`pnpm stack:dev`) cerca de 3,6 GB, com o `vmmemWSL` chegando a 6,4 GB. Aplicado `memory=8GB`, `swap=4GB` e `autoMemoryReclaim=gradual` no `.wslconfig`, mais `mem_limit` por serviço nos dois compose (cerca de 2x o pico medido). O WSL não sai do projeto: imagens Linux (Kafka, Postgres, Mongo, Debezium) exigem a VM Linux, e o Windows 11 Home não tem Hyper-V. **Como aplicar:** `.wslconfig` só vale após `wsl --shutdown`; `mem_limit` só vale após recriar o container; se um serviço morrer por OOM (exit 137), subir o limite dele em vez de tirar o teto do WSL. O WSL Settings do Windows edita o mesmo `.wslconfig`.
- [2026-10-27] Mover a pasta do projeto com uma sessão do Claude Code aberta nela falha (`Move-Item`: arquivo em uso), porque o cwd da sessão e os servidores MCP (npx do context7 e do chrome-devtools) seguram a pasta. **Como aplicar:** fechar a sessão antes de mover; o repo foi movido para `C:\Stubb\stubb` (confirmado em 2026-10-27) e a memória do Claude Code, presa ao path do projeto, vive agora em `~\.claude\projects\C--Stubb-stubb`.
- [2026-10-26] Debezium com `table.expand.json.payload=true` corrompe payload com lista de objetos heterogêneos (setor de pista com `capacity` e marcado com `rows` ganham campos nulos extras; `batches: []` some), e o projector estrito entra em loop de crash.
